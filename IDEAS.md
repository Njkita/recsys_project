# Каталог идей для максимизации NDCG@10 / HR@10 на ML-20M

Главный рабочий файл проекта. Цель — собрать всё, что даёт прирост по метрикам, отсортировано по ROI (impact / cost). Базовая точка отсчёта на ML-20M в full-catalog leave-one-out:

| Модель | HR@10 | NDCG@10 |
|---|---|---|
| Ванильный SASRec (BCE-1neg) | ~0.28 | ~0.10–0.12 |
| BERT4Rec (full softmax) | ~0.30 | ~0.135 |
| gSASRec (gBCE, n_neg=256) | ~0.33 | ~0.137–0.141 |
| eSASRec (LiGR + sampled softmax) | ~0.34–0.36 | ~0.145–0.155 |

Цель проекта — выйти на **HR@10 ≥ 0.34, NDCG@10 ≥ 0.14**, с амбицией на **NDCG@10 ≥ 0.15**.

## 1. Loss function — самая высокоимпактная группа

**gBCE (gSASRec)** — самый высокий ROI во всём каталоге. `t = 0.75`, `n_neg = 256`. Замена loss + увеличение негативов. Импакт **+15-20% NDCG@10** к ванильному SASRec, стоимость **дешёвая** (десяток строк). Это пункт номер один.

**Sampled softmax с logQ correction** (eSASRec). Cross-entropy с n=256 негативами + поправка по вероятности сэмплирования. Иногда обходит gBCE на 1-2%. Реализация чуть сложнее (нужен logQ).

**Full softmax по каталогу**. Физически реализуем при ~20k items (после 5-core), batch 128, L=200 — управляется через gradient checkpointing. В 5-10× медленнее sampled. Используется как «потолочный» эксперимент: проверить, что sampled softmax не теряет качества.

**Label smoothing** ε=0.1 — медиум-импакт +1-2%, копеечная стоимость. Совместим с CE/sampled softmax.

**Hard negative mining (DNS)**. Семплируем 1024 случайных кандидатов, считаем скоры, берём top-K (K=64) как «жёсткие». Импакт +2-4%, стоимость средняя (двойной forward).

**Mixed negatives**: 50% случайных + 25% popularity-weighted + 25% in-batch. Стабильно лучше чисто uniform.

**In-batch negatives** — почти бесплатно. Позитивы других элементов батча используются как негативы → эффективно умножает n_neg на B без памяти. Особенно хорошо при batch ≥ 256.

**Multi-task: next + next-next** (двухголовая). Sun et al. — +1-2%, средняя стоимость.

**Masked LM auxiliary к causal** — гибрид BERT4Rec + SASRec. Импакт средний, **удваивает время** обучения. На ML-20M экономически не оправдано после gBCE.

## 2. Архитектурные тюки — трансформер 2024 года

**Pre-LN вместо post-LN** — обязательный фикс для стабильности при `n_blocks ≥ 4`. Импакт по стабильности большой, по метрикам +1-2%, копеечно.

**RMSNorm вместо LayerNorm** (LLaMA-style). Чуть быстрее, метрики на уровне или микро-плюс.

**SwiGLU/GeGLU FFN** вместо ReLU+Linear (Shazeer 2020, прижилось во всех LLM). +1-3% NDCG. Стоимость дешёвая (увеличить hidden FFN в 2/3 раза для сохранения параметров).

**RoPE positional embeddings** вместо learned absolute. Критично для экстраполяции на длинные хвосты, +1-2% в среднем. **ALiBi** — альтернатива, проще, аналогичный импакт.

**LiGR / gated residual** (eSASRec): `x_out = gate * x + (1-gate) * F(x)`. Стабилизирует глубокие стеки. **+2-4%**, средняя стоимость.

**Multi-query attention / GQA** — ускоряет inference в 2-4×, метрики на уровне. Для оффлайн-метрик не критично, для прода — must.

**T5-style relative position bias**, **talking-heads attention** — каждый по +0.5-1.5%, менее критичны, чем RoPE+SwiGLU+LiGR.

## 3. NextItNet-сторона (если делаем эту задачу)

**Gated activations (GTU `tanh⊙σ` или GLU)** вместо ReLU — wavenet-style, +1-3%. Дешёвая замена.

**Skip connections от каждого блока к выходу** (DenseNet aggregation). +1-2%.

**Tied input/output embeddings** — must-have. Экономит `|I|·d` параметров, +1-3% NDCG. RecBole-имплементация этого не делает, мы добавим.

**Dilated rate scheduling** — два прохода `[1,2,4,8,1,2,4,8]` лучше одного `[1,2,4,8]` при том же бюджете блоков (показано в paper).

**StackRec для NextItNet** — оригинальная мотивация авторов StackRec. Тренируем 8 блоков → удваиваем до 16 → 32 → 64. Speedup растёт с глубиной (×3 на 64 блоках).

## 4. Эмбеддинги и side info

**Tied weights** input embedding ↔ output projection. Обязательно.

**Scaled init** — Xavier с √d или truncated normal с σ=0.02 (LLaMA). Стабильнее дефолтов.

**Embedding dropout** (по позициям, p=0.1-0.3). +1-2%.

**Side info из ML-20M — недооценённый источник прироста**. ML-20M содержит:
- `genres` — 19 жанров, one-hot или embedding (sum-pool)
- `year` из заголовка фильма — embedding декады (8-10 buckets)
- `tags.csv` — user-generated теги, частотный фильтр
- `genome-scores.csv` — **готовые 1128-мерные релевантностные векторы от Tag Genome**, лежат прямо в датасете

Embedding жанров + декады + проекция genome-vector в d, **склеенные с item-ID embedding через сумму** (или конкатенацию + linear) → даёт устойчивые **+2-4% NDCG**. Одна из самых высокоимпактных идей, упускается потому, что чистые SASRec-бейзлайны игнорируют side info. Стоимость — день работы.

**Two-tower hybrid** — расширение идеи (история юзера + контентный вектор товара). Стоимость средняя.

## 5. Обработка последовательностей

**max_len**: 200 — стандарт. **500** даёт +1-2% на ML-20M (длинные хвосты у активных юзеров), но 6× память attention. С RoPE + FlashAttention практично. Идти на 500 — после того, как остальное собрано.

**SSE-PT** (Stochastic Shared Embeddings, Wu et al., RecSys 2020) — с вероятностью p подменяем `user_id` или `item_id` случайным токеном из словаря. **Сильнейший регуляризатор для reco, +2-4% NDCG, 3 строки кода**. Очень рекомендую.

**Аугментации последовательности** (CL4SRec, DuoRec): random crop, item mask (BERT-style), item drop, reorder. По +1-2% каждая. С contrastive loss — до +5%. Стоимость средняя (нужен contrastive head).

**Reverse sequence** — спорный, для causal моделей принципиально не должен помогать; на ML-20M эмпирически не помогает. Не рекомендую.

**Curriculum (short → long)** — медиум-импакт, ускоряет сходимость, итоговые метрики мало меняет.

## 6. Расписание обучения

**AdamW** > Adam (decoupled weight decay), +0.5-1.5%.

**Lion** (Chen 2023) — потенциально быстрее по wall-clock, требует тюнинга lr (в 3-10× меньше AdamW). Не первым делом.

**Adafactor** — только при ограниченной памяти.

**LR**: 1e-3 peak + warmup 5-10% шагов + cosine decay до 1e-5. Импакт +2-3%, минимальная стоимость.

**Weight decay**: 1e-2 для AdamW. Внимание: PyTorch AdamW имеет особую семантику wd — на эмбеддинги items decay часто **не** прикладывают.

**Batch size**: 256-512 sweet spot. >1024 ухудшает обобщение даже с gradient accumulation.

**Эпохи**: 100-300 типично. С early stopping по val NDCG обычно сходится за 50-100.

**AMP**: bf16 на A100 — однозначно. fp16 рискует overflow в softmax-логитах.

**Gradient clipping**: норма 1.0 — must-have, особенно при gBCE.

**EMA весов** (decay 0.999 или 0.9995) — почти всегда +0.5-1% на финальных метриках. Включать.

## 7. Негативное семплирование

**n_neg = 256** — sweet spot для ML-20M.

**Popularity-weighted negatives** (вероятность ∝ frequency^0.75, как word2vec) — +1-2% к uniform. Заставляет модель различать популярные близкие альтернативы.

**Adaptive (увеличивать n_neg по эпохам)** — почти не отличается от константного 256 с самого начала.

## 8. Эвалюация — это не оптимизация, но критично

**Full-catalog with filter-already-seen** — единственный честный путь. Krichene & Rendle (KDD 2020) формально доказали, что sampled-100 не сохраняет ранжирование моделей.

**Filter already-seen items** — обязательно. Без фильтрации модель тривиально предсказывает любимые перепросмотры, метрики раздуваются.

**Temperature scaling** — не влияет на ранжирование (монотонное преобразование), не нужно.

**Reverse-rank truncation** — оптимизация (partial argpartition вместо argsort), без эффекта на метрики.

## 9. Данные ML-20M

**Все рейтинги → события** (canon gSASRec) или **rating ≥ 4 как позитивы**. Берём первое — каноничнее.

**Сессии по timestamp** (split при разрыве > 30 минут) — может помочь как доп позиционный сигнал. Средний импакт.

**Popularity feature** как явный input — спорно, модель её и так выучивает.

## 10. Ансамбли

**Среднее предсказаний SASRec + NextItNet** — классический трюк, **+1-2% NDCG почти всегда**.

**Snapshot ensembling** (Huang et al., ICLR'17) — чекпойнты на дне каждого cosine-цикла, усреднение. **+1-1.5%, бесплатно по обучению**.

**Multi-seed averaging** (3-5 сидов) — +0.5-1.5%, дорого по compute, но важно для статистически валидных публикаций.

## 11. Масштабирование (StackRec)

**Шире vs глубже на ML-20M**: обычно `d=256, n_blocks=2-4` побеждает `d=64, n_blocks=8`. `|I|×d` упирается в выразительность эмбеддингов. Идти в ширину до d=256-384, потом в глубину.

**StackRec для глубины** — после того, как ширина исчерпана.

## 12. Регуляризация

**Dropout placement**: attention 0.2, FFN 0.2, embedding 0.1-0.3, residual 0.1. SASRec по умолчанию 0.2 везде — разумная отправная точка.

**Stochastic depth (DropPath)** для глубоких стеков ≥ 6 блоков — +0.5-1%, дешёвая.

**Mixup на эмбеддингах** — экспериментально, нестабильно на reco. Не первый приоритет.

## Топ-5: если только пять вещей

Если бюджет ограничен и нужно выбрать **пять приёмов с максимальным ROI**:

### 🥇 1. gBCE с `n_neg=256` и `t=0.75` (gSASRec)

Самый высокий ROI во всей таблице. **+15-20% NDCG@10** относительно ванильного SASRec. Десяток строк кода. **Без этого все остальные оптимизации меркнут.** Это абсолютный пункт номер один.

### 🥈 2. Side info через ML-20M genome-scores + жанры + декада года

Контентный embedding склеенный с item-ID embedding. **+2-4% NDCG**. Редко применяется в чистых SASRec бейзлайнах. День работы. Данные уже в датасете (`genome-scores.csv`, `movies.csv`).

### 🥉 3. Современный training stack

AdamW + warmup-cosine + bf16 + gradient clipping + EMA. В сумме **+3-5% NDCG** относительно дефолтного `Adam(lr=1e-3)`, плюс стабильность. Каждый компонент копеечный.

### 4. Архитектурный апгрейд: Pre-LN + RMSNorm + SwiGLU FFN + RoPE + LiGR

Пакет «трансформер 2024 года». В сумме **+3-6% NDCG**. 2-3 дня работы. Стартовать с **Pre-LN + RoPE** (главные два), потом доехать до SwiGLU и LiGR.

### 5. SSE-PT + embedding dropout + правильная full-catalog evaluation с filter-seen

SSE-PT — **бесплатные +2-3%**. Embedding dropout — ещё +1%. Правильная эвалюация защищает от ложных выводов и обязательна для воспроизводимости. «Гигиенический» пункт, без которого первые четыре нельзя честно измерить.

---

**Итог.** Эти пять блоков должны вывести SASRec-бейзлайн с `HR@10 ≈ 0.28 / NDCG@10 ≈ 0.16` на уровень `HR@10 ≈ 0.34-0.36 / NDCG@10 ≈ 0.20-0.22`, что соответствует или превосходит опубликованные числа eSASRec/gSASRec на ML-20M.

> ⚠️ Цифра NDCG@10=0.16 как baseline для ванильного SASRec встречается в одних воспроизведениях, в других baseline ~0.10-0.12 — разница из-за деталей сплита (LOO vs time-based) и фильтра rating≥4 vs all. Зафиксировать препроцессинг — единственный способ получить сравнимые цифры.

Дальнейшие приёмы (contrastive аугментации, ансамбли, mixed negatives, DNS) добавят ещё 2-4% с убывающей отдачей. Это **вторая волна** экспериментов после того, как фундамент собран.

## Методологический момент (не идея, но важно)

При сравнении с Данилом и публикациями **обязательно** зафиксировать:
- порог рейтинга (≥4 или все)
- минимум взаимодействий (5-core)
- LOO vs temporal split
- фильтрация уже виденных при evaluation

Метрики SASRec в литературе разнятся **в полтора раза** только из-за деталей сплита. Лучшая защита — воспроизвести RecBole или конкретно gSASRec-репозиторий Petrov как точку отсчёта, и потом по одному добавлять трюки из этого каталога с фиксированными остальными гиперпараметрами. Именно поэтому первый шаг проекта — **прочитать препроцессинг в TOPAPEC/esasrec и записать его дословно** в `RESEARCH.md` секцию 6.
